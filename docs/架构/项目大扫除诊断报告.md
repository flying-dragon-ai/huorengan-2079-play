## 3. 终极 `.gitignore` 与 `.gitattributes`

### 3.0 先纠正一个误解

你的要求里写"结合重构后的新目录（如 `app/`, `domain/`, `infrastructure/`）"给忽略规则——**这四个目录一个都不该出现在 `.gitignore` 里**。

`app/` `domain/` `infrastructure/` `shared/` 是**源码分层**，是仓库最该跟踪的东西。`.gitignore` 管的是"生成物、缓存、机器本地状态"，跟源码怎么分层完全无关。把源码目录写进 ignore 是自毁。

真正需要按新目录调整的只有三处，而且都是**产物目录搬家**：

| 产物 | 现在 | 迁移后 |
|---|---|---|
| 验收截图 | `_shots/` | `tests/e2e/shots/` |
| 生成任务产物 | `tripo-out/` | `tools/tripo/out/` |
| 构建产物 | `dist/` | `dist/`（不变） |

所以下面的模板**同时兼容当前布局和迁移后布局**——两套路径都写进去，迁移时不用再改 `.gitignore`。

## 4. 死代码检测命令

### 4.1 已交付的零依赖脚本（推荐）

```bash
node tools/ci/check-orphans.mjs
```

它做真实的可达性分析，不是字符串匹配：

1. 从 `index.html` / `viewer.html` 的 `<script type="module" src>` 抓入口
2. 对 `src/` 建 import 图（`from '...'` 与 JSDoc `import('...')` 都算）
3. DFS 求可达集，差集就是孤儿
4. 资产侧：汇总 `src/` 里出现的文件名、`MODEL_CONF` 的 `file` 字段、`gen/manifest.json` 的登记项，差集就是未引用资产

实测输出（当前仓库）：

```
入口：src/main.js, src/viewer/main.js
扫描 64 个 JS、62 个资产。
孤儿 JS 0（基线内 0）
未引用资产 8（基线内 8）

✓ 没有新增孤儿。
```

**基线机制**：`tools/ci/orphans.baseline.json` 记录已知的合法例外（那 8 个管线中间产物）。新增孤儿会失败，逼你二选一——删掉，或显式加进基线并写清理由。基线里失效的条目会提示清理。

### 4.2 手工速查（rg，本机已装）

```bash
# ---- 1. 某个文件被谁引用？（把 X 换成文件名）----
rg -n "from ['\"].*X\.js['\"]" src/ tests/ tools/ scripts/

# ---- 2. 找已入库但本该忽略的东西 ----
git ls-files | rg '^(dist|_shots|tripo-out)/' | head -20
git ls-files | rg '\.(log|tmp|cache)$'

# ---- 3. 找大文件（确认没有漏网的非 LFS 大文件）----
#     LFS 文件在 Git 里是 ~130 字节指针，所以「blob > 1MB」=「>1MB 且没走 LFS」
git ls-files -s | awk '{print $2, $4}' \
  | git cat-file --batch-check='%(objectsize) %(rest)' \
  | awk '$1 > 1048576 {printf "%.1f MB  %s\n", $1/1048576, $2}' | sort -rn

# ---- 4. 找注释里指向已删除文件的路径 ----
rg -n "tools/serve\.py|build_portable|browser/build\.py|app/main\.js" \
   --glob '!node_modules' --glob '!*.md'

# ---- 5. 找 export 了但没人 import 的符号（单进程，快）----
node -e '
const fs=require("fs"),path=require("path");
const walk=(d,out=[])=>{for(const e of fs.readdirSync(d,{withFileTypes:true})){const p=path.join(d,e.name);e.isDirectory()?walk(p,out):p.endsWith(".js")&&out.push(p);}return out;};
const defs=walk("src");                       // 定义只可能来自 src/
const all=[...defs,...walk("tests")]          // 使用方还要算上 tests/
  .map(f=>fs.readFileSync(f,"utf8")).join("\n");
const seen=new Map();
for(const f of defs){const t=fs.readFileSync(f,"utf8");
  for(const m of t.matchAll(/export\s+(?:const|function|class)\s+(\w+)/g)){
    const n=m[1];seen.set(n,(seen.get(n)||0)+1);}}
const W="[^A-Za-z0-9_$]";
for(const [n,c] of seen){
  const uses=(all.match(new RegExp("(^|"+W+")"+n+"("+W+"|$)","g"))||[]).length;
  if(uses<=c) console.log("只定义未使用: "+n);
}'
```

> **别用 shell 循环遍历文件。** 本机每次 spawn 约 50–90 ms，`for f in $(find src -name '*.js')` 这种写法 64 个文件就是 5 秒起，加上 `rg` 内部再扫一遍，实测 30 秒还没跑完。上面第 5 条用单个 Node 进程一次读完所有文件，0.2 秒。
>
> 同理，**孤儿文件检测不要手写循环**——`node tools/ci/check-orphans.mjs` 已经做了正确的可达性分析，比任何 grep 组合都准（grep 会把注释里的路径也算成引用）。
>
> **第 5 条为什么用 `[^A-Za-z0-9_$]` 而不是 `\b`**：`node -e '...'` 里的 `"\\b"` 经过 shell 会塌成 `"\b"`，而 JS 字符串里的 `\b` 是**退格符 U+0008**，不是词边界。第一版我写的就是 `new RegExp("\\b"+n+"\\b")`，结果 204 个导出全被报成"未使用"——正则匹配了 0 次，`uses=0 <= c` 恒成立。字符类写法不需要任何反斜杠，绕开整个转义问题。
>
> 实测当前仓库：**204 个具名导出，6 个只定义未使用**（见 §1.2 M7）。

### 4.3 为什么不推荐 knip / depcheck

| 工具 | 问题 |
|---|---|
| **knip** | 为 npm 生态设计，默认假设有 bundler（webpack/vite/rollup）配置。本项目是**原生 ESM + importmap + esbuild 单文件打包**，knip 找不到入口配置，要么误报一片，要么得写一堆 `entry` / `project` 覆盖。而且它要装 30+ 个传递依赖，与"运行时零 npm 依赖"的洁癖相冲 |
| **depcheck** | 只查 `package.json` 的依赖是否被用，**不查文件级死代码**。本项目 devDependencies 只有 4 个（esbuild/eslint/prettier/vitest），全都在用，depcheck 跑出来是空的 |
| **`eslint-plugin-unused-imports`** | 查的是"文件内 import 了但没用"，不是"文件没人 import"。两回事 |

`check-orphans.mjs` 只有 190 行、零依赖、按本项目的入口约定写死，比配 knip 便宜得多。

## 5. 防再犯：CI 加固

### 5.1 把孤儿检测挂进 `ci.yml`

在 `Lint` 之前插一步（架构级问题比风格问题更该先失败）：

```yaml
      - name: 孤儿检测
        run: node tools/ci/check-orphans.mjs

      - name: 分层与循环依赖
        run: node tools/ci/check-layers.mjs

      - name: Lint
        run: npm run lint
```

`package.json` 加两条脚本：

```json
"scripts": {
  "check:orphans": "node tools/ci/check-orphans.mjs",
  "check:layers": "node tools/ci/check-layers.mjs",
  "check": "npm run check:orphans && npm run check:layers && npm run lint && npm test && npm run build && npm run build:viewer"
}
```

### 5.2 再加一道"产物不许入库"的守卫

孤儿检测管代码，这条管 Git 索引。放进 `ci.yml`：

```yaml
      - name: 产物不许入库
        run: |
          set -euo pipefail
          bad=$(git ls-files | grep -E '^(dist/|_shots/|tripo-out/|tests/e2e/shots/|tools/tripo/out/)' || true)
          if [ -n "$bad" ]; then
            echo "::error::以下产物被提交进 Git，请 git rm --cached："
            echo "$bad"
            exit 1
          fi
          logs=$(git ls-files | grep -E '\.(log|tmp)$' || true)
          if [ -n "$logs" ]; then
            echo "::error::日志/临时文件被提交："
            echo "$logs"
            exit 1
          fi
          echo "✓ 索引干净"
```

### 5.3 再加一道"大文件必须走 LFS"的守卫

```yaml
      - name: 大文件必须走 LFS
        run: |
          set -euo pipefail
          # LFS 文件在 Git 里存的是 ~130 字节的指针，所以「blob 体积 > 1MB」
          # 天然等价于「>1MB 且没走 LFS」。一条管道搞定，不逐文件 spawn。
          offenders=$(git ls-files -s \
            | awk '{print $2, $4}' \
            | git cat-file --batch-check='%(objectsize) %(rest)' \
            | awk '$1 > 1048576 {printf "%.1f MB  %s\n", $1/1048576, $2}')
          if [ -n "$offenders" ]; then
            echo "::error::以下文件 >1MB 但没走 LFS："
            echo "$offenders"
            exit 1
          fi
          echo "✓ 大文件全部走 LFS"
```

> **别用 `stat` 逐文件循环**。第一版我写的是 `git ls-files -z | while read; do stat ...; done`，本机实测 800 多个文件 spawn 800 次子进程，跑了 20 秒还没完。`git cat-file --batch-check` 一次进程读完所有 blob 体积，实测 **1.8 秒**。
>
> 当前仓库跑出来只有 2 条，都是预期内的：`dist/活人感2079.html`（3.6 MB，出库后消失）和 `vendor/three/three.core.js`（1.4 MB，vendored 第三方，故意不走 LFS）。

### 5.4 四道守卫的分工

| 守卫 | 拦什么 | 失败时怎么办 |
|---|---|---|
| `check-orphans.mjs` | 新增没人 import 的 JS / 没人引用的资产 | 删掉，或加进 `orphans.baseline.json` 并写理由 |
| `check-layers.mjs` | 反向依赖、跨层跳跃、循环依赖 | 改 import 方向 |
| 产物/日志守卫 | `dist/` `_shots/` `tripo-out/` `*.log` 被提交 | `git rm --cached` |
| LFS 守卫 | >1 MB 的二进制没走 LFS | `git lfs track` 后重新 add |

四道加起来不到 60 行 YAML，零额外依赖，覆盖了这次审计发现的全部问题类型。
